# frontend/CLAUDE.md — правила фронтенда

Уточняет корневой [`CLAUDE.md`](../CLAUDE.md) для `frontend/`. Общие правила (язык, роль, вопросы, git) — там.

## 1. Стек и команды

React 19 + TypeScript + Vite. Роутинг — react-router v8, серверное состояние — TanStack Query, HTTP — axios, состояние в URL — nuqs, клиентское состояние — zustand, формы — react-hook-form + zod, тексты — i18next, стили — SCSS-модули, тесты — vitest + Testing Library.

Все команды запускаются из `frontend/`:

| Задача                                               | Команда                                              |
| ---------------------------------------------------- | ---------------------------------------------------- |
| Dev-сервер (`/api` проксируется на `localhost:8000`) | `npm run dev`                                        |
| Линтер (oxlint, предупреждения = ошибки)             | `npm run lint`                                       |
| Форматирование                                       | `npm run format` (проверка: `npm run format:check`)  |
| Типы                                                 | `npm run typecheck`                                  |
| Тесты                                                | `npm run test:run` (в режиме наблюдения: `npm test`) |
| Сборка                                               | `npm run build`                                      |
| Витрина компонентов                                  | `npm run dev` → `/ui-kit`                            |

## 2. Архитектура: FSD

Слои сверху вниз: `app` → `pages` → `widgets` → `features` → `entities` → `shared`.

- Слой импортирует только из слоёв **ниже** себя. Слайсы одного слоя друг друга не импортируют (`features/a` не знает про `features/b`).
- Каждый слайс открывает наружу только свой `index.ts`. Импортировать из чужого слайса глубже его `index.ts` нельзя.
- Импорты — через алиас `@/`, без длинных относительных путей (`../../../`).
- Куда что класть:
  - `shared` — без бизнес-смысла: UI-кит, `apiClient`, i18n, утилиты, токены;
  - `entities` — сущности предметной области (участник, лот, пул) и их отображение;
  - `features` — действия пользователя (вступить в пул, внести залог);
  - `widgets` — крупные блоки экрана (шапка, полоса пула);
  - `pages` — экраны.

## 3. Дизайн

### 3.1. Скилл impeccable — обязателен

- **Перед любой дизайн-задачей вызови скилл `impeccable`.** Дизайн-задача — это новый экран или блок, вёрстка, визуальные стили, новый UI-компонент, правка внешнего вида.
- Если скилла `impeccable` нет среди доступных — **остановись** и попроси пользователя установить его: `npx impeccable install`. Без скилла дизайн не делаем, этот шаг не пропускаем.
- Чистая логика без изменений внешнего вида (хуки, запросы, стор) скилла не требует.

### 3.2. Дизайн-система

- Компоненты — в `src/shared/ui`, импорт только из `@/shared/ui`. Перед тем как верстать, загляни в `/ui-kit`: возможно, нужное уже есть.
- **Дизайн-система готова не на 100%.** Если нужного компонента нет — создай его сам, строгости тут нет. Условия:
  - строй на токенах из `src/shared/styles/tokens.scss` (CSS-переменные) и миксинах из `_mixins.scss`, без захардкоженных цветов, радиусов и длительностей;
  - повторяй визуальный язык существующих компонентов: таблетки, `--radius-card`, акцент `--accent`, нажатие через `@include pressable`;
  - универсальный компонент — в `shared/ui` с экспортом в `shared/ui/index.ts` и примером на `/ui-kit`. Компонент с бизнес-смыслом — в `entities` или `features`;
  - учитывай `prefers-reduced-motion` (`@include reduced-motion`), видимый фокус и aria-атрибуты, как в существующих компонентах.
- Стили — только SCSS-модули (`Component.module.scss`), имена классов в camelCase. Глобальные стили — только в `app/styles`.
- Брейкпоинты — миксины `lg` / `md` / `sm` (1180 / 900 / 560 px), ховер — `@include hover`.
- В `shared/ui` нет бизнес-правил. Например, какой рейтинг считать высоким, решает `entities`, а `TrustBadge` получает готовый `level`.

## 4. Данные и бизнес-логика

- **Фронтенд не считает залог, рейтинг, допуск и деньги** — он показывает цифры от бэкенда (см. корневой `CLAUDE.md` §2). Не копируй формулы из макета или PRD в клиентский код.
- Запросы к серверу — через `apiClient` из `@/shared/api` и TanStack Query. Ключи запросов и функции запросов живут рядом с сущностью (`entities/<name>/api`).
- Ответы API типизируй. Если данные пришли не той формы — ошибка должна быть видна, без тихих фоллбэков.
- zustand — только для клиентского состояния, которого нет на сервере и в URL. Фильтры, шаги и выбор, которые должны переживать перезагрузку, — в URL через nuqs.
- Формы — react-hook-form + zod-схема через `@hookform/resolvers/zod`.

## 5. Тексты и i18n

- Пользовательские тексты — через `useTranslation()`, без строк прямо в JSX. Исключения — витрина `/ui-kit` и тесты.
- Ключи — в `src/shared/i18n/locales/{ru,uz,en}.json`. **`ru` и `uz` обязательны**: в демо есть переключатель языка. `en` по возможности, без перевода показывается `ru`.

## 6. TypeScript и React

- Никаких `any` в рабочем коде. Если тип неизвестен — `unknown` и сужение.
- Пропсы типизируются прямо в сигнатуре функции, без `React.FC`.
- Не подавляй ошибки линтера и типов без причины. Если подавление неизбежно — точечно, на одну строку и с объяснением.

## 7. Тесты

- Тест лежит рядом с файлом: `Component.test.tsx`.
- Ищи элементы по роли и тексту (`getByRole`, `getByLabelText`), действия — через `userEvent`. Тестируй поведение, а не реализацию.
- Обязательно покрываем логику: хуки, преобразование данных, интерактивные компоненты. Чисто визуальные компоненты тестами не покрываем.
